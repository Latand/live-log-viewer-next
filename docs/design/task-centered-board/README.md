# Task-centered board — visual slice

Implementation notes for [`../task-centered-board.md`](../task-centered-board.md) (issue #1586): the board slice (bands, ranking, anchored zoom) plus the durable admission that gives every conversation a task.

## What changed

- **One horizontal band per task.** `src/components/scheme/taskBands.ts` projects recorded task membership, pipeline and flow containers, native lineage roots and open drafts onto bands, and lays the ordered bands out top to bottom at the full available width. Members wrap into rows; a band's height follows its members. `TaskBandsLayer.tsx` draws the band chrome; the existing node, slot, deck, draft and group layers draw the members at the rectangles the band layout assigns.
- **Semantic zoom with hysteresis.** Below 22% every member is a one-line chip; 22–81% shows title/status tiles; from 82% the selected conversation mounts its real reader while its siblings stay tiles. The crossings carry a two-point margin, so a wheel resting on a threshold never oscillates. Text and controls are counter-scaled, so zoom changes density, never legibility.
- **Canonical membership.** `src/lib/tasks/membership.ts` is the single writer: `ensureTaskMembership` resolves explicit targets, then a task whose admission origin key matches, then a task already holding a canonical assignment for the identity (the conversation id decides first, so a resume successor with a fresh launch id keeps its conversation's task and its original launch record), then a task held by a participant the launch inherits from, and otherwise mints one placeholder with a `linked` assignment in the same task-file transaction. Placeholders carry `origin {kind, key, refinement}`, are exempt from the per-project task limit, and a replay of the same origin key converges on the same task. Every launch path — operator drafts, agent-initiated spawns, pipeline stages, review-flow rounds, resume successors — reserves its durable launch receipt through `AgentRegistry.beginSpawnRequest`, after its own admission checks and before any actuation. That reservation commits the launch's membership with the reserved launch and conversation identity (`src/lib/tasks/launchMembership.ts`): explicit task targets travel on the request (`taskIds`, set by a band-local «+ Agent» through the HTTP spawn route and by the dedicated task spawn route) and are joined in their own project without any fallback; a pipeline stage joins the pipeline's recorded tasks; a reviewer joins the tasks the reviewed conversation holds (a flow round therefore lands in its implementer's task, and a flow whose implementer has none gets one fallback task binding implementer and reviewer together); a task-less pipeline gets one fallback task; everything else one placeholder keyed by the client attempt (or the launch id for keyless launches), in the launch's validated explicit project when it has one and otherwise the project the scanner derives for its directory. A membership the store cannot record retires the fresh receipt and aborts the launch. A retry of the same attempt must name the same target set; a changed or added target is refused. A queued pinned launch that is recovered for its first execution passes the same prerequisite again before actuation: the membership recorded at reservation converges, a receipt older than the rule or one whose task was deleted while it waited is bound then, and an unavailable store fails the receipt instead of starting an agent outside every task. The scanner's admission pass remains as the repair path for a transcript whose receipt keys are held by a task but whose identity write was lost, and as the import path for transcripts that never went through a Viewer launch. Scanned conversations without any membership are admitted on the scanner's durable controller pass in batches of 50: a root gets one placeholder titled from its first prompt, a child joins the task its parent holds (planned once the parent is covered, so parent and child never split across two placeholders; a child whose parent transcript is gone gets its own placeholder), and an agent-initiated launch joins its parent's task at the reservation the same way. A pipeline without task ids claims one fallback task for its container, and the pipeline controller records that fallback on the pipeline's own `taskIds` — at the stage reservation, before the agent is actuated, and on every tick for pipelines admitted by the scanner — so the task/pipeline read model and the assignment binding see one pipeline for the task instead of requesting another. Nothing is written from a read-only GET.
- **Last membership on unlink and delete.** Detaching a conversation's last assignment binds it to a replacement placeholder in the same task-file snapshot, keyed by that row's admission origin (the launch key when the row came from a Viewer launch, otherwise the conversation) so a replay of the launch converges on the replacement; detaching it from the placeholder that is its own admission is refused, because the replacement would be that task again. Deleting a populated task applies the same rule to every conversation it alone held. A conversation still linked elsewhere, and a failed row, need no replacement.
- **Authoritative ranking.** A band's working count is the number of distinct conversations whose provider turn is open. A fresh mtime, a live process, a spawning receipt or a host-claimed attempt is `unknown` and contributes zero; a closed turn is idle. Bands sort by working count, then task creation, then id. A newly created card therefore never ranks as running.
- **Screen anchor.** The camera hook records the selected projection's screen position on every commit and, when the next commit finds it at a different world position or zoom, translates the camera before paint so both coordinates hold, mode crossings and re-wraps included. Explicit framings (fit, focus glide, jump, Return) re-baseline instead. Gesture and button zoom keep the band's left edge in place, since the world is exactly one viewport wide; only the anchor correction may offset it, and horizontal panning brings it back. Fit All frames the overview from the top at chip scale, Fit Current the top (working) bands at tile scale.
- **Interaction-aware reordering.** Rank moves are deferred while the operator pans or types inside the board; status labels update at once. When the deferred order differs, an «Order updated» control applies it.
- **Add-agent in context.** Every band ends with a local «+ Agent» (in the header at overview scale). It opens the existing launch form seeded with the task text; the draft is seated in the band and, once the launch has a transcript with a real path, the assignment is recorded through the existing task assignment route. That route adopts the conversation into the task's pipeline record with `autoStart: false`; it spawns nothing.
- **Shared conversations.** A conversation linked to several tasks has one reader owner, canonically in the earliest-created task's band; the other bands show a dashed reference tile naming the primary task. Opening the conversation from a reference tile hosts the one surface in that band (the tile's slot becomes the member's, the canonical band shows the tile in return), so the operator keeps the task context they clicked in; composer and delivery owner are unchanged. The anchor is keyed by projection (band and conversation) and the clicked tile primes it, so the surface lands on the tile's screen point while the bands around it reflow. Shared running work counts once per linked task.
- **Membership provenance.** Recorded assignments and explicitly bound containers (pipeline `taskIds`, or a fallback task minted for that container) establish members. An execution the projection associated only through one matching worker stays a relation; its other stages are not promoted into the task.
- **Cross-task relations.** A recorded lineage edge whose endpoints lie in different bands is shown as a labelled continuation under each endpoint (and under mirrors of it), naming the other task; following it selects the other endpoint. The overview header carries the count instead of chips.
- **Every surface fits its band.** A member wider than the band's inner width (a 600px draft pane or planned stage slot on a board the orchestrator dock has narrowed, a deck, a reader tile) is scaled down uniformly, rendered contents included, so no surface extends past the band that holds it; the fitted box is what the layout, visibility index and mirrors read.
- **Deferred reordering covers reading, too.** Rank moves wait while the operator pans, types, holds a text selection inside the board, or has a disclosure or action menu open; status labels update at once and the «Order updated» control applies the pending order, which also applies by itself when the interaction ends.
- **Container halos stay in their band.** A pipeline or flow halo is a projection inside the band that owns it: it wraps the container's members placed in that band and that band's mirrors of its other members, never a surface hosted in another band.
- **First-action refinement.** Every placeholder starts with `refinement: pending` (its admission title is the first prompt line or the container goal, kept as a placeholder). The MCP server instructions tell every agent to make its first Viewer action `update_task` with `refine: { text }`; the binding resolves the caller's own pending task(s) from its server-derived conversation identity, applies a short title plus up to two lines once, returns `replayed` for the same text again and `already-named` for a task an operator edit or an earlier refinement already titled. An operator's text edit names a pending placeholder for good.

## Still open

- Transcripts that never went through a Viewer launch (externally started CLIs, imported history) are admitted on the scanner's controller pass after they exist; until that pass reaches one, the board shows it in a band derived from its lineage root, labelled "no task yet", as projection only.
- The refinement is prompted through the MCP server instructions every agent receives; an agent without Viewer tools keeps its placeholder title until an operator edit.

The PNG frames stay local: the publication gate accepts only rasters it can reproduce from a deterministic generator, and browser screenshots are not that. Reproduce with:

```
bun run build
bun scripts/capture-issue-1586-task-bands.ts            # dense: 25 tasks / 100 conversations
BANDS_DENSITY=six bun scripts/capture-issue-1586-task-bands.ts
```

Frames land in `<tmp>/llv-issue-1586-*/out`; the evidence JSON is rewritten in this directory.

Unit and DOM coverage: `src/lib/tasks/membership.test.ts` (placeholder, replay, identity fill, explicit targets, limit exemption, admission planning, 1,000 imports in batches, interrupted durable pass), `src/lib/tasks/launchMembership.test.ts` (attempt/launch keys, explicit project, bound pipeline tasks, container fallbacks, failure retires the receipt), `src/app/api/spawn/membership.test.ts` (explicit target committed at reservation, refusal and unwritable store abort it, cross-site request rejected before any commit), `taskBands.test.ts` (membership, provenance, mirrors, host overrides, continuations, ranking, hysteresis, wrapping at 375–1920, +Agent placement, 350 tasks / 1,000 conversations), `SchemeBoard.bands.dom.test.tsx` (mounted ranking, chip mode, both-axes anchor through wheel/toolbar/mode crossings, zoom without a selection, band-local add-agent), and the adjusted camera suite.

## Limits

- The 350-task / 1,000-conversation case is covered by the pure layout test, not by a browser run.
- Pipelines and review flows are exercised by the existing DOM suites (their halos and header controls sit inside the task band); the capture fixture seeds tasks and transcripts only, because pipelines are persisted in SQLite.
- A hand drag can pan horizontally after an anchor correction offset the band; zoom itself never opens a gap beside the band.
